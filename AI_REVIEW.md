# AI_REVIEW.md

## 1. Использованные AI-инструменты

В процессе разработки и проверки проекта использовался **ChatGPT** в качестве технического помощника.

Основные задачи, для которых применялся AI:

- разбор требований тестового задания и составление плана реализации;
- проектирование структуры Docker Compose и Dagger-модуля;
- подготовка конфигураций Prometheus и Grafana;
- помощь с написанием скриптов автоматизации и проверки состояния;
- анализ ошибок Docker, Docker Compose и Dagger;
- разбор логов контейнеров и результатов проверок;
- подготовка документации по запуску и эксплуатации проекта.

AI использовался как инструмент для ускорения разработки и поиска решений, но его рекомендации не принимались автоматически. Команды выполнялись в реальном окружении, а результат проверялся по состоянию контейнеров, логам, Prometheus Targets и ответам Grafana API.

## 2. Примеры использованных промптов

В ходе работы применялись запросы нескольких типов.

**1. Разбор задания и планирование архитектуры**

«Разбери тестовое задание, составь план реализации и объясняй поэтапно, какие инструменты использовать, как они взаимодействуют и зачем нужны».

Результат: был определён состав проекта, разделение на два независимых Compose-слоя, использование Dagger для управления развёртыванием и Prometheus/Grafana для наблюдаемости.

**2. Разбор ошибок при запуске**

«Вот вывод терминала после выполнения команды Dagger. Разбери, на каком этапе произошла ошибка, объясни причину и предложи безопасное исправление, не затрагивающее данные в Docker volumes».

Результат: использовался для диагностики проблем с путями проекта, Docker socket, образами и настройками монтирования.

**3. Проверка конфигурации мониторинга**

«Проверь конфигурацию Prometheus и Docker Compose. Объясни, почему targets могут быть недоступны и как проверить, что экспортёры действительно отдают метрики».

Результат: проверялись конфигурации scrape-targets, доступность экспортёров и соответствие метрик запросам Prometheus.

**4. Проверка фактического результата**

«Проанализируй результат `dagger call check-status`. Какие проверки прошли, какие предупреждения остались и что они означают для работы проекта?»

Результат: удалось отделить работоспособность основных компонентов от ограничения cAdvisor на Docker Desktop для macOS.

**5. Подготовка документации**

«Обнови README с учётом фактических команд запуска на macOS, параметров Dagger и обнаруженных ограничений мониторинга».

Результат: документация была приведена в соответствие с реально проверенным сценарием запуска.

## 4. Ошибки и спорные решения, обнаруженные в ходе работы

### Кейс 1. Dagger не мог прочитать домашнюю директорию macOS

**Проблема:**

При первом запуске Dagger пытался синхронизировать слишком широкую директорию пользователя. На macOS возникала ошибка доступа к каталогу в `Library/Application Support/FileProvider`:

```text
permission denied
```

**Причина:**

В рабочей директории находились системные каталоги macOS, доступ к которым ограничен механизмами безопасности и FileProvider.

**Решение:**

Проект был скопирован в отдельную рабочую директорию с простым ASCII-путём:

```text
/Users/petrkadetov/Downloads/Kadetov_Petr_DevOps
```

Дополнительно при вызове Dagger стал явно указываться исходный каталог проекта:

```bash
--src=.
```

**Результат:**

Dagger успешно загрузил проект, обнаружил функции модуля и выполнил команды развёртывания.

**Вывод:**

При работе с Dagger на macOS важно контролировать границы передаваемого контекста. Не стоит передавать всю домашнюю директорию, если для выполнения задачи достаточно каталога проекта.

### Кейс 2. Неверный тег образа cAdvisor

**Проблема:**

При запуске monitoring-слоя возникла проблема с загрузкой образа cAdvisor:

```text
ghcr.io/google/cadvisor:v0.55.1
```

**Причина:**

Использованный тег с префиксом `v` не соответствовал доступному тегу образа в реестре.

**Решение:**

В `docker-compose.monitoring.yml` тег был исправлен:

```yaml
image: ghcr.io/google/cadvisor:0.55.1
```

После исправления загрузка образа прошла успешно.

**Результат:**

Контейнер cAdvisor запустился и получил статус `healthy`.

**Вывод:**

Даже если версия программного обеспечения известна, нельзя автоматически предполагать формат тега Docker-образа. Его необходимо проверять по доступным образам и фактическому результату `docker pull`.

### Кейс 3. Несовместимое монтирование `rslave` на Docker Desktop для macOS

**Проблема:**

В конфигурации node-exporter использовалось монтирование:

```yaml
- /:/host:ro,rslave
```

На Docker Desktop для macOS этот вариант оказался несовместим с используемым окружением.

**Причина:**

Docker Desktop работает через Linux-виртуальную машину и не предоставляет все возможности Linux bind mounts в том же виде, что обычный Docker Engine на Linux.

**Решение:**

В `docker-compose.monitoring.yml` было изменено монтирование:

```yaml
- /:/host:ro
```

**Результат:**

Monitoring-слой успешно запустился. Node-exporter стал доступен и работал в состоянии `running`.

**Вывод:**

Конфигурации, рассчитанные на Linux, не всегда можно переносить на Docker Desktop без изменений. При разработке кроссплатформенного стенда необходимо отдельно учитывать особенности виртуализации Docker на macOS.

### Кейс 4. cAdvisor работает, но не отдаёт label `name`

**Проблема:**

После успешного запуска всех сервисов проверка `check-status` показала предупреждение:

```text
WARN cAdvisor не отдаёт label name
```

При этом сам контейнер cAdvisor находился в состоянии `healthy`, а соответствующий Prometheus target — `UP`.

**Причина:**

Особенность сбора метрик cAdvisor в окружении Docker Desktop для macOS. Контейнер может быть доступен, но часть метаданных контейнеров, необходимых для группировки метрик, отсутствует.

**Решение и проверка:**

Была выполнена проверка метрик в Prometheus:

```promql
container_cpu_usage_seconds_total
```

Также было проверено состояние всех targets.

Полностью устранить отсутствие label средствами текущей конфигурации на macOS не удалось. Ограничение было зафиксировано в README.

**Результат:**

Основные компоненты платформы работают, все targets находятся в состоянии `UP`, но панели CPU/RAM контейнеров могут быть пустыми.

**Вывод:**

Статус `UP` означает, что Prometheus успешно опрашивает target, но сам по себе не гарантирует наличие всех ожидаемых меток и метрик. Необходимо проверять не только доступность экспортёра, но и фактическое содержимое временных рядов.

### Кейс 5. Необходимо явно передавать исходную директорию в Dagger

**Проблема:**

Автоматическое определение исходного каталога Dagger оказалось неудобным в локальном окружении macOS. Без явного указания каталога возникала проблема с передачей лишних файлов и директорий.

**Решение:**

Для всех практических вызовов Dagger использовался параметр:

```bash
--src=.
```

Пример итоговой команды:

```bash
dagger call deploy-app \
  --src=. \
  --docker-sock=unix:///var/run/docker.sock \
  --env-file=file:.env
```

**Результат:**

Команды выполнялись из корня рабочей копии проекта. Dagger получал необходимый исходный каталог, а секреты передавались отдельным аргументом.

**Вывод:**

Явное указание исходной директории делает запуск более предсказуемым и упрощает воспроизводимость проекта.

## 5. Дополнительные технические наблюдения

### 5.1. Docker socket и Dagger

В ходе практического запуска использовался аргумент:

```bash
--docker-sock=unix:///var/run/docker.sock
```

Dagger успешно получил доступ к Docker socket и запускал Docker CLI внутри своего контейнера.

Это позволило управлять контейнерами Docker-демона хоста через Dagger-функции.

### 5.2. Передача секретов

Файл `.env` передавался в Dagger как Secret:

```bash
--env-file=file:.env
```

Это позволило не включать реальные пароли в команды и не хранить их непосредственно в конфигурациях Compose.

Файл `.env` исключён из `.gitignore`-контекста публикации и не должен включаться в итоговый архив.

### 5.3. Проверка подключения Uptime Kuma к MariaDB

Одного успешного запуска контейнера недостаточно, чтобы утверждать, что приложение использует нужную базу данных.

Поэтому дополнительно проверялись логи Uptime Kuma:

```text
Database Type: mariadb
Creating basic tables for MariaDB
Created basic tables for MariaDB
Connected to the database
```

Также `check-status` подтвердил наличие 28 таблиц в базе данных Kuma.

Это позволило подтвердить фактическое использование MariaDB вместо SQLite.

### 5.4. Проверка Grafana и Prometheus

После развёртывания мониторинга была выполнена настройка Grafana через API.

Проверка вернула:

```text
Data source «Prometheus» обновлён
Дашборд «Safeboard — здоровье контура» загружен
Проверка data source: 200 Successfully queried the Prometheus API.
Готово: найдено дашбордов: 1
```

Это подтвердило не только доступность веб-интерфейса Grafana, но и работоспособность соединения с Prometheus.

## 6. Итоговая оценка использования AI

AI оказался полезен при проектировании, подготовке конфигураций и диагностике проблем, особенно при работе с Dagger и различиями Docker Desktop на macOS и Linux.

При этом в процессе работы стало очевидно, что предложенное AI решение необходимо проверять в реальном окружении.

Наиболее важные выводы:

1. Конфигурация, корректная для Linux, не обязательно будет работать без изменений на macOS.
2. Успешный запуск контейнера не всегда означает, что приложение использует правильную базу данных или что экспортёр отдаёт все необходимые метрики.
3. Для диагностики необходимо сопоставлять вывод Docker, логи приложений, Prometheus Targets и сами метрики.
4. При передаче проекта другому разработчику важно документировать не только команды запуска, но и ограничения конкретной среды.

В итоге AI использовался как помощник при разработке и анализе, а технические решения принимались с учётом результатов фактического запуска.
